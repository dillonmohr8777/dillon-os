# Verifier, 2026-09-21

Every agent that produced a report today, checked against its own accept sentence
with the file open. Ten job rows in the ledger for 2026-09-21: three weekly, seven
daily. Hourly `daily-sweep` rows excluded, they are the watchdog, not a cadence
job.

## Lead: ledger rows claiming ok whose artifact could not be found

**One, and it turned out to be a path-resolution artefact, not a lie.**

`omega-search-terms` names
`clients/omega-landscaping/deliverables/2026-09-21 - search terms pages 1-5.md`.
Resolved against dillon-os, as the ledger's own schema comment implies
("repo-relative path"), that file does not exist. Resolved against
client-operations, which is where the job's `client` key routes it, it exists at
20,200 bytes and is committed as `7ef8502`, 323 insertions.

**Verdict: not a false ok.** The artifact is real and committed. But the ledger
does not record *which* repo a path is relative to, and a client-routed job writes
to a different repo than a vault job. Any automated reader that resolves ledger
paths against dillon-os will report this row as a lying ledger every single week.
That is a schema gap worth one line in `driver.md`; it is the only thing standing
between this check and a recurring false alarm.

**No other row claims an artifact that is absent, empty, or stale.** All nine
remaining artifacts exist, are non-empty, and are dated today.

### MEETS, with the line that proves it

- **`omega-search-terms`** requires page position recorded so the next run
  resumes. Line 11: "**Next run resumes at** | **page 6 (ranks 101-120)**", with
  line 10 fixing this run at "**1-5**, ranks 1-100 of 363 terms, sorted by cost
  descending". Classification requirement met, the findings separate competitor
  brands, supplier/materials brands, and cost/DIY shoppers, each with the spend
  and clicks attached.
- **`report-pairing-check`** requires a per-client table with last generated,
  last sent, and gap in days. 38 table rows; the header block defines both
  columns operationally ("newest on-disk send evidence: a delivery receipt with
  `sent_verified`, a verified Gmail `messageId`, or a `SENT-`/`sent-to-`
  artifact"), so the "sent" column is evidence-defined rather than assumed.
- **`revenue-exceptions`** requires that any unsourceable field reads "pending
  validation" and is never estimated. The string appears **16 times**, and the
  source table states each blocker exactly: SPEND `invalid_grant`, CRM HubSpot
  OAuth, LEADS partial. Nothing is estimated. This is the accept sentence working
  as designed, a job that could not get its data said so instead of inventing it.
- **`heartbeat`** requires naming every job due yesterday with its state, ABSENT
  first. Nothing was due Sunday; it says so, then leads with the eight absent
  job-days from Friday 2026-09-18.
- **`approval-queue-diff`** requires added, closed, newly overdue, and a total.
  All four present: 8 added, 0 closed, 8 removed undecided, 65 rotting of 137.
- **`unfiled-sweep`** requires per-repo counts and a named list of new
  deliverable-shaped arrivals. Both present, 67 arrivals grouped by client, all
  three ids resolved against the registry.
- **`leads-triage`** requires counts by class and a named table of only the real
  leads. Present: real 2 / duplicate 1 / noise 1, two named leads with contact
  details and source, and the duplicate pair with both timestamps.
- **`ops-decision-packets`** requires every blocked item to carry exactly one
  decision, evidence, a named responsible person, a deadline, and the cost of
  delay. All eight packets carry all five fields. Packet 6 records
  "**No single decider identified**" rather than guessing a name, which is what
  the manifest asks for when no owner exists.
- **`production-briefs`** requires a review link or a precise named blocker for
  every promised asset, with "in progress" disallowed. Fourteen items, every
  blocker names a person or states "no named owner"; none reads "in progress" or
  "TBD". The ANSWERED carry-forward requirement is met explicitly in item 9,
  where seven previously answered inputs are tabled rather than re-asked.
- **`delivery-milestones`** requires four separate state columns with independent
  evidence. All 23 rows carry four columns; 16 read "no evidence" in three of

## The one thing I would not sign off on

`heartbeat`'s **first** committed version (`9225b638`) called 2026-09-20 a
Saturday and reported 16 absent job-days across "two full weekdays". 2026-09-20
was a Sunday and only 2026-09-18 was a missed weekday, so the correct figure is
8. It was corrected and recommitted as `0ffaeac2` before this verifier ran, and
the commit message says what changed and why.

The artifact on disk now is correct and meets its gate. Recording it here anyway,
because a verifier that only ever reads the final state cannot tell the difference
between a report that was right and a report that was fixed, and the ledger note
for that row is the only place the correction survives.

## Cross-check the ledger does not catch

Three reports written today independently reached the same conclusion from
different sources, which is worth more than any of them alone:

- `delivery-milestones` found 16 client deliverables built 2026-09-14 with zero
  receipts, working forward from the filesystem.
- `report-pairing-check` found 13 of 26 active clients with no send evidence at
  all and nothing sent anywhere in 11 days, working from the registry.
- `revenue-exceptions` found 0 of 26 clients reconciling, working from the data
  sources.

Three methods, one answer: **the weekly client pipeline builds and does not
send.** No single job's accept sentence covers that, which is why it is here.
