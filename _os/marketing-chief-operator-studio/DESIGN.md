# Design System: Marketing Chief Operator Studio

## Overview

**Creative North Star: "The Operating Ledger"**

The Studio behaves like a living operations book laid open beside Dillon: exact, scannable, dense when the work demands it, and quiet enough that state and decisions remain obvious. Its visual language joins an editorial ledger's rules and notation with a modern control room's status vocabulary.

The interface is neither a generic card dashboard nor a decorative AI cockpit. Command navy establishes authority, working paper holds the day-to-day record, signal orange marks owner action, and precise mono notation makes queue revisions, confidence, dates, and state feel inspectable.

**Key Characteristics:**

- Dense, legible operational hierarchy
- Square ledger geometry and explicit dividers
- Navy command surfaces paired with warm working paper
- Orange reserved for owner action and current focus
- Mono notation for state, evidence, counts, and versions
- Responsive structure that turns into a mobile operating console

## Colors

The palette separates command, record, evidence, and state rather than decorating inactive surfaces.

### Primary

- **Command Navy:** Owns the sidebar, command surfaces, and high-authority controls.
- **Signal Orange:** Marks the current selection, the owner's primary action, and exceptional attention.

### Secondary

- **Evidence Blue:** Identifies informational evidence and connected-source state.
- **Verified Green:** Marks verified, healthy, completed, or ready states.
- **Attention Amber:** Marks review, warning, or unresolved human gates.

### Neutral

- **Working Paper:** The default app canvas.
- **Clean Surface:** Records, rows, fields, and working panels.
- **Primary Ink:** Main text and strong data.
- **Secondary Ink:** Explanations, metadata, and supporting labels.
- **Ledger Lines:** Structural boundaries; strong lines organize tables and major regions.

**The Signal Rarity Rule.** Orange belongs to owner action, active focus, or meaningful attention. It must not become ambient decoration.

## Typography

**Display Font:** Geist with Arial fallback  
**Body Font:** Geist with Arial fallback  
**Label/Mono Font:** Geist Mono with Consolas fallback

**Character:** One workhorse family keeps the operating surface familiar and fast. Mono is functional notation, never a costume.

### Hierarchy

- **Display:** Tight, bold view thesis used once per major operating view.
- **Headline:** Section and dossier titles with restrained contrast.
- **Title:** Work-item and client names that remain readable in dense layouts.
- **Body:** Compact operational copy; longer explanations stay below 75 characters per line where layout permits.
- **Label:** Small uppercase notation for queue revisions, status, evidence, confidence, and control labels.

**The Data Is Not Decoration Rule.** Mono appears only when the text behaves like state, a version, a count, a date, or an identifier.

## Layout

Desktop uses a fixed command rail, a sticky control bar, and a centered working canvas. Dense ledgers and split client workspaces preserve alignment across repeated records. Major views vary their structure according to the task rather than repeating a universal card grid.

At tablet widths, side-by-side dossiers stack and wide ledgers may scroll only inside their bounded region. Below 760px, the rail becomes persistent bottom navigation, command surfaces become single-column, and important actions remain thumb reachable. Mobile is a structural operating mode, not a shrunken desktop.

## Elevation & Depth

The system is flat by default. Borders, tonal fields, sticky position, and dark command surfaces establish depth. The one ambient shadow is reserved for command panels, sticky dossiers, and overlays that genuinely sit above the ledger.

### Shadow Vocabulary

- **Command Lift:** `0 22px 70px rgb(12 25 48 / 12%)` for high-authority panels and sticky client dossiers.
- **Overlay Lift:** `0 30px 100px rgb(0 0 0 / 30%)` for owner decision and instruction dialogs.

**The Flat Record Rule.** Ordinary rows and records never receive floating-card shadows.

## Shapes

Controls, ledgers, and panels use square corners. The sharp geometry makes the Studio feel like a deliberate working instrument and keeps dense records aligned. Circular geometry is reserved for status dots and avatars where the meaning is conventional.

## Components

### Buttons

- **Shape:** Square, compact, and explicit.
- **Primary:** Signal orange with white type for the owner's committed action.
- **Command:** Command navy with white type for safe execution or refresh.
- **Hover / Focus:** Color inversion or a clear three-pixel translucent orange focus ring; no decorative movement.
- **Secondary:** Transparent with a strong ledger border.

### Cards / Containers

- **Corner Style:** Square.
- **Background:** Clean Surface for records; Command Navy for briefing, dossier, and control-plane context.
- **Shadow Strategy:** Flat records, lifted command surfaces only.
- **Border:** One-pixel ledger lines, shared across adjacent records to create one continuous book.
- **Internal Padding:** Compact 16–24px records; 32–40px command regions on desktop.

### Inputs / Fields

- **Style:** White working field, one-pixel strong ledger stroke, square corners.
- **Focus:** Translucent orange three-pixel outline with two-pixel offset.
- **Error / Disabled:** Explicit red text or reduced opacity plus cursor feedback; state may not rely on color alone.

### Navigation

The desktop rail uses a navy field, white active text, muted inactive text, and an orange left rule for the current view. Mobile uses a fixed navy bottom rail with the same orange active indicator. Labels stay literal and task-oriented.

### Recommendation Ledger

The three governed lanes share a continuous ruled grid. Each item keeps client, action class, priority, next action, rationale, deadline, confidence, and available owner actions attached.

### Watchtower

Watchtower is the default operating view. The first viewport answers three questions in order: is the Chief healthy, what is it doing next, and what needs Dillon. Its command surface pairs a short live operating statement with the current cycle and next safe work. The seven-stage ruled spine follows as a compact vertical proof ledger: Watch, Exact route, Prioritize, Build, Verify, Learn, and Final gate. A state is green only when current telemetry supports it. Polling, queued, delayed, degraded, shadow, and unavailable remain literal.

The final-gate dossier is the one sticky authority surface: it shows the exact outside-world action still waiting after local work and verification are complete. Teach Sprint remains in the primary flow. Full outcome history, policy and prediction internals, the capability register, and the signal ledger use explicit disclosure rows so technical depth never buries the daily operating job. The signal ledger carries only redacted, allowlisted routing metadata.

### Teach Sprint and Outcome Episodes

Teach Sprint is a six-row decision folio, not a chat interrogation. Accept, defer, and reject are one-click version-bound judgments; modify opens the full editor. The episode ledger aligns prediction, owner judgment, verified reality, and learned adjustment so a click cannot masquerade as an outcome.

### Prediction Lab

The lab groups the twenty verified prediction capabilities into data, retrieval, evaluation, training, serving, and governance lanes. Promotion law is rendered as a strict sequence of data, smoke, shadow, statistical, security, canary, and rollback gates. “Shadow only” is a real state, not decorative copy.

### Client Dossier

The selected client opens as a high-authority navy workspace showing rank, route state, evidence confidence, active work, context, systems, and next action without blending another client's information.

### Portfolio Command

The owner command may target one active client or the full active portfolio. The portfolio choice is explicit and reports the exact fan-out count before submission. One portfolio instruction becomes one child task per active client; inactive clients are excluded, and every child retains its own route, evidence, queue record, and approval gate. In the command ledger, those children collapse into one portfolio run with waiting, completed, and failed counts plus a disclosure for the exact client routes.

## Do's and Don'ts

### Do:

- **Do** keep client identity visible beside every recommendation, queue item, request, and result.
- **Do** use density where Dillon is comparing work and quiet space where he is making a decision.
- **Do** make status, stale state, and approval gates explicit in words as well as color.
- **Do** preserve one component vocabulary across desktop and mobile.
- **Do** contain wide evidence ledgers inside their own scroll regions so mobile never expands the document viewport.

### Don't:

- **Don't** replace operational structure with generic analytics cards.
- **Don't** use gradients, glow, glass, or decorative motion as substitutes for information.
- **Don't** scatter orange across inactive regions.
- **Don't** hide consequential actions behind ambiguous icon-only controls.
- **Don't** make mobile a read-only afterthought.
